# 币安量化终端 · U 本位永续自动化交易机器人平台

一个**零第三方依赖**的本地 Web 平台（Node 24 内置模块实现），用于运行基于「账户权益 × 无量纲系数」的自动网格加仓机器人。

- **实时行情**：默认直连币安 `fapi.binance.com` 拉取全市场报价，30 个高成交额标的按成交额自动排序；断网时自动降级为本地模拟行情并在页面提示。
- **模拟模式**：本地撮合，不需要 API Key，随时可试；模拟盘余额可在「账户」页随时自定义（默认 100 USDT）。
- **实盘模式**：填写币安 U 本位合约 API Key 后，实时调用真实账户与下单接口。
- 参数全部由前端表单自定义，也有推荐默认值；下单金额**永不写死**，始终按实时权益等比缩放。

```bash
cd B:\biance_trae
node server.js
```

然后用浏览器打开 **http://127.0.0.1:8787** ，注册一个账号即可使用。

## 策略说明（这是本平台的核心）

用户原始想法：专注一个币种、全仓、以总资金的一定比例做多和做空各一份，价格每涨/跌一定比例就止盈一侧、加仓另一侧。

平台把它抽象成**完全无量纲**的参数化模型——同一套参数在 100U 和 10000U 账户上行为完全等比，**代码里没有任何硬编码的 U 数**：

| 参数 | 含义 | 默认 |
|---|---|---|
| `direction` | `dual` 双向 / `long` 只做多 / `short` 只做空 | `dual` |
| `allocatedCapital` | **分配给这个机器人的资金（USDT）** | 100 |
| `firstPct` | 第一笔保证金占「分配资金」的比例 | 1% |
| `leverage` | 杠杆 | 20x |
| `growRatio` | 每加一次仓，金额是上一次的几倍 | 1.5 |
| `spacingPct` | 加仓间距（价格相对实际均价走多少 % 加一次） | 1% |
| `maxLayers` | 最多加仓几笔（上限，不是一开始就建满） | 6 |
| `totalPct` | 单方向名义 / 分配资金 上限 | 3.0 |
| `maxLossPct` | 跌到止损位时的亏损 / 分配资金 上限 | 35% |
| `tpMode` | `avg` 整体止盈 / `layer` 逐笔止盈 | `avg` |
| `tpPct` | 止盈幅度（相对当前实际均价） | 0.5% |
| `stopPct` | 止损幅度（相对当前实际均价） | 5% |
| `interval` | 决策周期 | 5m |

**为什么有 `allocatedCapital`（问题 #3）**：一个账户可以开多个机器人，如果每个机器人都按账户总权益算仓位，账户资金会被重复分配，多开一个就多一份爆仓风险。所以每个机器人只能动用「分配给它的资金」：

- 仓位尺寸全部按 `allocatedCapital` 算，不按账户权益；
- **累计占用闸**：开首笔和每次加仓前都校验「本机器人已占用保证金 + 本笔 ≤ allocatedCapital」，超了就拒绝并写一条事件；
- 账户钱包（模拟盘）仍是共享的，`availableBalance = 钱包余额 − 所有机器人已占用`，只是每个机器人自己的上限是它的分配资金。

**最小名义校验（问题 #4）**：币安要求单笔名义 ≥ 5 USDT。创建/预览/改参数时如果 `allocatedCapital × firstPct% × leverage < 5`，直接判「参数不可行」并给出中文原因，不会等到下单才报 -1111。

**最小可下单金额（按数量步长算，比 5U 更严）**：5 USDT 只是名义下限，数量还有 `minQty` 与 `stepSize` 的限制。以 SKHYNIXUSDT 为例：`minQty=0.01`、`stepSize=0.01`，价格 976 时「0.01 个」这一最小单位就值 **9.76U**，所以低于 9.76U 的单根本下不出去（数量会被归整成 0）。平台现在用：

```
最小可下单金额 = max(exchangeInfo.minNotional, ceil(minQty/stepSize) × stepSize × 现价)
```

预览、创建、改参数、以及机器人 tick 时都会用它判定「第一笔/加仓能不能下出去」，不可行时直接告诉你要把「分配资金」或「第一笔保证金占比」调到多少。

求解链：

1. `资金基数 capital = allocatedCapital`（缺失才回退账户权益）
2. `首笔保证金 m1 = capital × firstPct%`，`首笔名义 = m1 × leverage`
3. 各层名义 `= 首笔名义 × growRatioⁱ`
4. 层数 `n` 从 `maxLayers` 往下试，取第一个满足三条约束的：单方向名义 ≤ `totalPct × capital`；跌到止损位亏损 ≤ `maxLossPct% × capital`；止损价必须在强平价之前触发
5. **价格锚点 `anchorPrice`**：计划一旦生成就固定，之后阶梯触发价不再随行情漂移（问题 #7）。完全平仓后才重新取锚点。
6. **止盈价永远按「当前实际持仓均价」现算**：`均价 × (1 ± tpPct%)`。绝不用「加满后的预测均价」，否则只开 1 笔时止盈价会落在现价错误一侧，开仓即平。
7. **止损价**：`stopPct` 幅度价与「强平价留 20% 缓冲」取更早触发的那个，并强制夹在入场价与强平价之间（`safeStop`）。

`direction = dual` 时，空头腿是多头腿的**完整镜像**：空头各层触发价 `= 锚点 × (1+spacing)ⁱ`，止盈 `= 空头实际均价 × (1 − tpPct%)`，止损在入场价上方、强平价下方。

> 早期版本只算了多头腿，空头误用多头的止损价，导致空单一开仓就被判定为触发止损、反复开平。该问题已修复。

### 实盘的止盈止损是真挂单（问题 #10）

实盘机器人每次 tick 都会用 `placeConditional` 在币安上挂 **TAKE_PROFIT_MARKET / STOP_MARKET** 条件单（`workingType=MARK_PRICE`），并维护 `state_json.condOrders` 记录自己挂出的单：

- 数量只填**机器人自己那一份**，不用 `closePosition`，绝不误平用户手动仓；
- `clientOrderId` 由「侧 + 类型 + 触发价 + 数量」派生，同样的意图永远同一个 id，网络超时重发会被币安按重复 id 拒掉；
- 触发价或数量变了就换新 id，先撤旧单再挂新单；
- 账户页「止盈价 / 止损价」两列在实盘下**直接读币安真实挂单**，没挂就显示「—」，估算值会标「估算」。

**强平价是近似估算**，实际以币安返回为准。上实盘前务必先用最小资金验证。

## 安全说明

- API Key / Secret 用 **AES-256-GCM** 加密后落库，任何接口都不回传明文，前端只显示脱敏值。
- 密码用 **scrypt + 每用户随机盐**，校验走 `timingSafeEqual`。
- 会话 Cookie：`HttpOnly; SameSite=Lax; Path=/`。
- 所有 SQL 参数绑定，所有写接口校验资源归属。
- 登录失败限流：同用户名 5 次 / 分钟。
- 平台默认只监听 `127.0.0.1`，不对外暴露。
- **实盘下单总开关默认关闭**：未设 `LIVE_TRADING=1` 时，即使 API Key 已验证，实盘机器人也会被拒绝启动（`LIVE_DISABLED`），绝不向真实账户发单。

### 实盘仓位是怎么界定的（重要）

币安 U 本位**双向持仓**模式下，同一个交易对的「多头」是**账户级聚合**的：`positionRisk`
只会告诉你「HYPEUSDT 多单 4.37 张」，分不清其中哪些是机器人开的、哪些是你手动开的。

本平台的做法是给每个实盘机器人单独记一本**持仓账本**（存在该机器人的 `state_json.liveLegs`）：

- 机器人每次开仓成功，把这一笔（数量、成交均价、层数）记进账本；
- 每次平仓，按数量从账本里扣掉；
- 每个 tick 与交易所实际持仓对账：
  - 交易所数量 **多于**账本 → 多出来的认定是**手动仓**，机器人在持仓里标「手动」，**绝不平它**；
  - 交易所数量 **少于**账本 → 你手动平掉了一部分，账本按比例缩减，不会去平不存在的仓位；
  - 你在币安上把仓位全平了 → 账本清零，机器人下个 tick 发现没仓位就重新从第 1 笔开始。

所以：**手动仓位和机器人仓位可以共存**，机器人只管理自己开的那部分。
风险提示：平仓时用的是市价 `reduceOnly` 单，如果手动仓和机器人仓方向相同，
币安会先从同一个持仓里扣减，账面上看是「一起变少」，这是交易所的聚合机制，不影响盈亏归属。

### 上实盘前的必做清单

1. 先在**币安测试网**或**最小资金**账户跑通。
2. API Key 只开「合约交易」权限，**不要开提现权限**，有条件就绑定 IP 白名单。
3. 确认 `firstPct`（第一笔保证金占比）、`totalPct`（单方向最多投入）、`maxLossPct`（最坏亏损上限）、`leverage` 的组合在自己能承受的回撤范围内。
4. 启动实盘机器人时会自动把该交易对的杠杆设置成参数里的值，并写一条事件日志。
5. 本机网络无法访问币安域名时，行情会自动降级为模拟值并在页面明确提示，不会静默下单或伪造数据。

## 常见问题

**Q：打开页面提示「前端资源尚未就绪」？**
A：`src/static/` 下缺少前端文件，检查是否完整拷贝了项目。

**Q：实盘账户页显示「未配置 API Key 或网络不可达」？**
A：两种情况——(1) 还没在 API Key 页添加并验证密钥；(2) 本机网络访问不了币安域名（中国大陆常见）。平台会降级展示，不会崩溃。

**Q：开实盘机器人报 `Parameter 'reduceonly' sent when not required`（-1106）？**
A：双向持仓（Hedge Mode）下币安不允许平仓单带 `reduceOnly`，方向由 `positionSide` 决定。已修复：只有单边持仓模式（`positionSide=BOTH`）才传 `reduceOnly`。

**Q：报 `Timestamp for this request is outside of the recvWindow`（-1021）或 `was 1000ms ahead of the server's time`？**
A：本机时钟和币安服务器有偏差，走代理时偏差更容易放大。平台现在的处理：
1. 启动时 `startTimeSync()` 每 60 秒（`BINANCE_TIME_SYNC_MS`）用 `/fapi/v1/time` 往返中点校准一次时钟偏移，所有签名请求的 `timestamp` 都用「本机时间 + 偏移量」；
2. `recvWindow` 可通过 `BINANCE_RECV_WINDOW` 调大（默认 5000，最大 60000），代理链路慢时建议设 10000；
3. 收到 -1021 / -1022 会**强制立刻重新对时**再重试一次。
服务器上还建议 `chronyc tracking` 确认系统时间本身没有被虚机拖慢。

**Q：报 `精度超出资产定义`（-1111 / -4164）？**
A：数量小数位必须 ≤ 该交易对 `stepSize` 允许的位数。2026-10-26 用户就跑出过这个问题（SKHYNIXUSDT，股票类永续，价格约 979），根因是两层 bug 叠在一起，现已全部修掉：

1. **合约筛选用错了条件**：`exchangeInfo` 里股票 / 商品类合约的 `contractType` 是 `TRADIFI_PERPETUAL`，而旧代码只接受 `PERPETUAL` 并跳过其余所有类型 → 这类合约查不到规则 → 静默降级成兜底规则。现在只排除交割合约（`CURRENT_QUARTER` / `NEXT_QUARTER`）与非 `TRADING` 状态的。
2. **兜底规则的小数位偏错**：旧兜底值是 `stepSize: 0.001`（3 位小数），而该合约真实是 `0.01`（2 位小数）；名义 15U / 价 979 → 数量 0.01532，按 0.001 floor 成 `0.015`（3 位）→ 币安直接拒单。

现在的四层保护：

1. **精度来源**：`parseFilters` 同时读 `LOT_SIZE` 与 `MARKET_LOT_SIZE`，取更粗的一档（本平台开平仓都是市价单）；
2. **规则持久化**：成功拉到 `exchangeInfo` 就写 `data/rules-cache.json`，服务重启 / 币安临时不通时先用上次的真实规则，**不再退回 0.001 兜底**；
3. **超时单独放宽**：`exchangeInfo` 响应约 1.1MB / 1000+ 合约，走代理容易超过普通接口的 8s/20s 阈值，这里单独给 30s；
4. **降精度重试**：真遇上 `-1111` / `-4164` 时，`placeOrder` / `placeConditional` 会把数量（以及条件单触发价）的小数位逐档减 1 重发，最多 4 档。**币安对精度的拒绝代表订单未被接受，因此重发不会造成重复开仓。**

另外预览与详情页原先写死了 `{stepSize:0.001}` 去估算计划，现在实盘机器人一律走真实 `exchangeInfo`，所以页面上看到的第一笔数量就是能下出去的数量。

**Q：网络超时后会不会重复开仓（问题 #1）？**
A：不会。三层保护：① 下单用**确定性 clientOrderId**（机器人+侧+层+动作+5 分钟桶），重发会被币安按重复 id 拒掉；② 网络错误/`-1007`/重复 id 时用 `queryOrder(origClientOrderId)` 回查真实结果，查到就当成功；③ POST 下单**绝不自动重试**，只有 GET 和撤单会重试。

**Q：为什么我的手动仓没被机器人平掉？**
A：这是设计。实盘机器人维护自己的 `liveLegs` 账本，平仓只平账本里那一份数量，数量列标「手动」的就是你自己开的仓。

**Q：忘记密码？**
A：直接删除 `data/app.db` 里对应的 `users` 记录，或整个删除 `data/` 重新初始化（**会清空所有机器人和历史**）。
