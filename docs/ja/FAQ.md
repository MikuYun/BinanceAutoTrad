# よくある質問（FAQ）

> 動かし始めてから最もぶつかりやすい問題をここにまとめました。初めての方はまず [QUICKSTART.md](QUICKSTART.md)、戦略の原理は [STRATEGY.md](STRATEGY.md)、配備・HTTPS・バックアップは [DEPLOY.ja.md](../../DEPLOY.ja.md) を参照してください。

## 一、インストールと起動

### Q1：何をインストールする必要がありますか？Node のバージョンはどのくらい必要で、なぜ 22.5 未満ではだめなのですか？

必要なのは **Node.js** だけです。それ以外は何もいりません。**22.5 以上**が必須で、**Node 24 LTS** を推奨します（`package.json` に `"engines": { "node": ">=22.5.0" }` と書かれています）。

22.5 が境界なのは、プログラムが Node 内蔵の `node:sqlite` でデータベースを保存しており、このモジュールが**22.5 からしか存在しない**ためです。バージョンが低いと起動時に次のエラーがそのまま出ます：

```
Error [ERR_UNKNOWN_BUILTIN_MODULE]: No such built-in module: node:sqlite
```

確認方法は `node -v` です。`v22.5.0` 以上が表示されれば合格、`v18.x`/`v20.x` ならアップグレードが必要、「コマンドが見つかりません」と出たら未インストールです。インストール後は**ターミナルを閉じて開き直して**ください。そうしないと環境変数が反映されません。

### Q2：`npm install` は必要ですか？

**不要です。** 本プロジェクトはサードパーティ依存ゼロで、`node_modules` すら生成されません。3 つのコマンドはそのまま実行できます：`node server.js` でサービス起動、`node scripts/check.js` で全ファイルの構文チェック、`node --test scripts/` で単体テストの実行です。

### Q3：Windows ではどう起動しますか？

**PowerShell** を使ってください（cmd は環境変数の書き方が違うので使わないでください）：

```powershell
cd B:\biance_trae
node server.js
```

「监听地址：127.0.0.1:8787 / 实盘下单：已关闭（安全闸，只读）」（待ち受けアドレス：127.0.0.1:8787 / 実弾の発注：無効（安全ゲート、読み取り専用））と表示されれば成功です。ブラウザで <http://127.0.0.1:8787> を開いてください。macOS / Linux も同じで、プロジェクトディレクトリへ `cd` してから `node server.js` を実行します。

### Q4：ポート 8787 が使用中と言われたら？ポートはどう変えますか？

エラーに `EADDRINUSE` が出ていれば占有されています。方法は 2 つです：

```bash
# 方法 1：占有しているプロセスを見つけて終了する
ss -lntp | grep 8787            # Linux/macOS、PID を取得したら kill
netstat -ano | findstr :8787    # Windows、続けて taskkill /PID <PID> /F
```

```powershell
# 方法 2（推奨）：ポートを変える
$env:PORT=9000; node server.js          # Windows PowerShell
PORT=9000 node server.js                # macOS / Linux
```

変更後は `http://127.0.0.1:9000` にアクセスします。

### Q5：`HOST` とは何ですか？なぜ他の人のスマホからアクセスできないのですか？

`HOST` のデフォルトは `127.0.0.1` で、**このマシンからしかアクセスできない**という意味です。これは安全のためのデフォルト値です。LAN 内の端末からアクセスさせたい場合にのみ `0.0.0.0` に変更してください。そして**公網からのアクセスには HTTPS リバースプロキシが必須**です。`8787` をそのまま外部に露出させないでください（[DEPLOY.ja.md](../../DEPLOY.ja.md) の第 5 節を参照）。

### Q6：ターミナルウィンドウを閉じるとサービスが停止しますか？

はい、そのウィンドウがサービスそのものです。**閉じれば停止します。** 常駐させる方法は、Linux なら systemd（[DEPLOY.ja.md](../../DEPLOY.ja.md) 第 4 節）、Windows ならタスクスケジューラです。

良い知らせとして、サービス再起動後は**状態が「运行中」のボットが自動的に復旧**し、イベントログに「服务重启，机器人已恢复运行」（サービス再起動、ボットは稼働を再開）と記録されます。

## 二、アカウントとログイン

### Q7：最初のアカウントはどう登録しますか？

ホームページを開く → 「注册」（登録）タブ → 2 項目を入力：ユーザー名は**3〜32 文字**の英字／数字／アンダースコア、パスワードは**6〜128 文字** → 「注册并登录」（登録してログイン）をクリックすると、登録成功と同時に**そのままログイン**します。

これは**純粋にローカルなアカウント**で、自分のマシンの `data/app.db` にのみ存在します。メールアドレスも電話番号も不要で、どこにもアップロードされません。

### Q8：パスワードを忘れたら？「尝试次数过多」と表示されたら？

**パスワード再発行機能はありません**。アカウントデータはローカルにしかなく、検証に使えるメールアドレスも存在しないためです。方法は 2 つだけです。`data/app.db` を削除してやり直す（全データが失われます）か、コードが書けるならデータベースを直接修正する（パスワードは `scrypt$盐$哈希` の形式で `users` テーブルに保存されています）かです。**登録時にパスワードを必ず控えておいてください。**

「尝试次数过多，请 N 秒后重试」（試行回数が多すぎます。N 秒後に再試行してください）はブルートフォース対策です。**同一ユーザー名で 1 分間に最大 5 回まで失敗**でき、表示された秒数が過ぎてから再試行してください。ログイン状態は **7 日間**保持されます（Cookie 名は `bt_sid`、`httpOnly` 付きなのでスクリプトからは読めず、Cookie の窃取を防ぎます）。

## 三、ペーパーモード

### Q9：ペーパーモードと実弾モードは具体的にどこが違いますか？

| | ペーパーモード | 実弾モード |
| --- | --- | --- |
| 資金 | 仮想資金。いくらでも設定可能 | 実際の USDT |
| 約定 | プログラムがローカルで約定を模擬 | 実際に Binance へ発注 |
| 価格 | **実弾モードと同じリアルタイム相場** | リアルタイム相場 |
| 手数料 | 0.05% 固定で計算 | 実際のあなたの手数料率で控除 |
| スリッページ | 0.02% 固定 | 実際の板の厚みで決まる |
| リスク | ゼロ | 全額失う可能性あり |

**初回は必ずペーパーモードから**始めてください。流れとレイヤー表を理解してから実弾モードを検討してください。

### Q10：ペーパーモードの価格は本物ですか？

**本物です。** デフォルトでは Binance 先物の相場に直接接続します。Binance にアクセスできないネットワークの場合にのみ、**自動的にローカル模擬価格へ降格**し、ページ上にその旨を表示します。強制的にローカル模擬価格を使う（オフラインでのデモ）には：`$env:BINANCE_FEED="mock"; node server.js`。

### Q11：ペーパーモードの残高はどう変更しますか？

「账户」（口座）ページ → 右上の「设置模拟余额」（ペーパー残高を設定）。ルールは、最小 **10 USDT**（下回ると「模拟资金不能小于 10 USDT」＝模擬資金は 10 USDT 未満にできません、と表示）、最大 **10,000,000 USDT**、口座開設時のデフォルトは 100 です。

⚠️ デフォルトの処理方式は「重置钱包，并清空所有机器人的持仓」（ウォレットをリセットし、すべてのボットのポジションを消去）です。**残高を変更すると、すべてのペーパーボットのポジションと注文が消えます。** このウォレットは**アカウント単位**で、すべてのペーパーボットが 1 つの残高を共有します。各ボットはさらに自分自身の「このボットに割り当てた資金」で動かせる上限を制限され、同じ資金を重複して賭けることを防ぎます。

### Q12：ペーパーモードの手数料とスリッページはどう計算されますか？実弾モードより楽観的になりますか？

ハードコードされた 2 つの定数があります：手数料 **0.0005**（各約定の名目に対して 0.05%、建玉と決済でそれぞれ 1 回）、スリッページ **0.0002**（約定価格と仲値の差 0.02%）。したがって建玉から決済までの往復コストは約 **0.14%** です。利確を 0.1% に設定すると、稼いだ分で手数料を払えません。

ペーパーモードは「成行注文が即座に全量約定し、スリッページは固定」という前提で、板の厚み不足、部分約定、極端な相場での注文拒否は考慮していません。**そのため大きなポジションではペーパーモードの結果が実弾モードより楽観的になります。** ペーパーモードの収益を実弾モードの期待値としないでください。

## 四、ボットと戦略

### Q13：ボット作成時に「参数不可行」と出るのはなぜですか？

インターフェースは具体的な中国語の理由を返します。最も多いのは次の 3 つです：

1. **初回が小さすぎる**：初回の名目金額が、この銘柄の最小発注金額を下回っています。例：割当資金 5 U ＋ 初回 1% ＋ 20 倍 = **1 U** では、5 U のハードルすら超えられません。
2. **初回が重すぎる**：初回の名目が割当資金の 400% を超えています（例：初回 20% × 20 倍 = 400%）。
3. **初回の時点で「単方向の総投入上限」を超えている**。

仕組み上の理由：初回の名目 = 割当資金 × 初回比率 × レバレッジ。もっと大きな初回にしたいなら、**割当資金を増やす、初回比率を上げる、レバレッジを上げる**のいずれかです。メッセージには「いくつ以上にすればよいか」が直接計算されて表示されるので、そのとおりに変更してください。

### Q14：「最小可下单金额」とは何ですか？

Binance は各注文に**2 つの下限**を設けており、プログラムは大きいほうを採用します：

```
最小可下单金额 = max(交易所最小名义额, 数量步长向上取整 × 步长 × 当前价格)
```

- **最小名目額**：多くの先物では **5 USDT**。名目 = 数量 × 価格であり、**証拠金ではありません**。
- **数量ステップ**：この先物で発注できる最小の数量単位です。例えばステップが 0.01 なら、最低 0.01 枚から発注できます。

例：ある先物の価格が **976 USDT**、ステップが **0.01** の場合、最低 0.01 枚 = **9.76 USDT** となり 5 U より大きいため、実際のハードルは **9.76 U** です。これが「割当資金 24 U ＋ 初回 1% ＋ 20 倍 = 4.8 U」で建玉できない理由で、ほんの少し足りません。

### Q15：ボットを作ったのに、なぜずっと動かないのですか？

**おそらく正常です。** このボットは「価格が計画上の位置に来てから動く」ように設計されています。ポジションがないときは最初の tick で初回を建て、その後は価格が**買い増しライン**に達したら買い増し、**利確／損切りライン**に達したら決済します。途中で数時間動かないのは普通のことです。

「详情」（詳細）ページで**イベントログ**を確認してください。各ラウンドの判断と理由がすべて書かれています。初回すら建っていない場合は 2 点を確認してください：① 初回金額が最小発注金額を満たしているか。② ペーパーウォレットの**可用残高**がこの証拠金に足りているか（足りないと注文は拒否され、ログに「开仓被拒：账户可用余额不足」＝建玉拒否：口座の可用残高不足、と記録されます）。

### Q16：なぜ最初からレイヤーが埋まらないのですか？レイヤー表には 5 層と書いてあるのに

**レイヤー表は「計画」であり「約定済み」ではない**からです。プログラムは一度に **1 筆**しか建てず、価格が実際に次の買い増しラインに到達して初めて次の 1 筆を建てます。表の各行は「価格がここまで来て、この 1 筆を買い増したら、買い増し後の平均価格／利確／損切りがいくつになるか」という予測です。

また、**設定したレイヤー数がそのまま全部使えるとは限りません**。6 層に設定しても、それ以上買い増すと設定した「最大損失」や「単方向の総投入」の上限を超えるため、プログラムが 5 層しか算出しないことがよくあります。プレビューとログには「层数从 6 自动降到 5」（レイヤー数を 6 から 5 に自動で減らしました）と明示されます。

### Q17：「整体止盈」と「逐笔止盈」はどう選びますか？

| モード | 決済方法 | 向いている人 |
| --- | --- | --- |
| **全体（デフォルト）** | **現在の実際の建玉平均価格**が＋利確幅に達したら、一度に全量決済 | 大多数の人。シンプルで手数料も抑えられる |
| **逐筆** | 各 1 筆が自分のエントリー価格の上に達したら個別に決済 | 前のほうの 1 筆を先に確定させ、建玉量を減らしたい人 |

逐筆モードは手数料がより多くかかり、最後の数筆がずっと待たされることもあります。

### Q18：プレビュー表の利確価格が、実弾モードで見る価格と違うのはなぜですか？

**意図的であり、そうしなければなりません。** 利確価格の計算には「**現在の実際の建玉の平均価格**」を使い、「買い増し完了後の予測平均価格」は使いません。

買い増し完了後の予測平均価格で計算すると、1 筆しか建てていないときに算出される利確価格が現在価格の**誤った側**に位置し、その結果**建玉した瞬間に決済されてしまい**、手数料を一度無駄に払うことになります。したがって利確は現在の実際の建玉から計算する必要があります。詳しくは [STRATEGY.md](STRATEGY.md) の第 7 節を参照してください。

### Q19：1 アカウントで最大何個のボットを作れますか？「停止」「重置」「删除」はどう違いますか？

最大 **20 個**です（超えると「最多创建 20 个机器人」＝作成できるボットは最大 20 個です、と表示）。操作の違いは次のとおりです：

| 操作 | ポジション | 台帳 | 使う場面 |
| --- | --- | --- | --- |
| **停止** | デフォルトでは維持。「同时平仓」（同時に決済）にチェック可 | 維持 | 一時的に止めたいとき |
| **リセット** | ペーパーモードは全消去。実弾モードは**取引所のポジションを決済しない** | 消去し、0 層から再計算 | やり直したいとき |
| **删除** | リセットと同じ | 注文・イベント・曲線もまとめて削除 | このボットが不要になったとき |

⚠️ **実弾モードの「リセット」の落とし穴**：ボット自身の台帳だけを消去し、取引所上のポジションは残ります。再起動後、これらのポジションは「**手動ポジション**」とみなされ、ボットは管理しなくなります。利確も損切りもしてくれません。

パラメータを変更するには**必ず先にボットを停止**してください（稼働中は「请先停止机器人再修改参数」＝先にボットを停止してからパラメータを変更してください、と表示されます）。

## 五、実弾モードと API Key

### Q20：API Key はどう入力しますか？

Binance 公式サイト → API 管理 → API Key を作成（「系统生成」＝システム生成、を選択）→ 本プログラムの「API Key」ページ →「添加」（追加）：メモ（任意。最大 40 文字）、API Key、API Secret（**Binance では一度しか表示されません**）。

保存後に「**验证**」（検証）をクリックし、「验证通过，合约账户权益 X USDT」（検証成功、先物口座の資産 X USDT）が表示されて初めて設定完了です。Secret は後からでも構いません（状態が「待补全」＝補完待ちになります）が、**Key だけ入れて Secret を入れないと残高を取得できません**。Binance の口座系 API は Secret による署名が必須です。

### Q21：API Key にはどの権限を有効にすればいいですか？

| 権限 | 必要か | 説明 |
| --- | --- | --- |
| 読み取り（Read） | ✅ 必要 | 残高・ポジションの取得 |
| 先物取引（Enable Futures） | ✅ 必要 | 発注・取消・レバレッジ設定 |
| 現物取引 | ❌ 不要 | 本プログラムは現物取引を行いません |
| **出金（Withdraw）** | ❌ **絶対に不要** | ボットに出金は一切必要ありません |
| IP ホワイトリスト | ✅ 強く推奨 | 自分のサーバーの IP のみ許可 |

**「出金禁止」を鉄則にしてください**。Key が漏洩した場合の最悪のケースは勝手に取引されることであり、資金を直接送金されることはありません。

### Q22：実弾モードの起動で `LIVE_DISABLED` が出るのはなぜですか？

原文：

> 实盘下单安全闸未开启：服务启动时需设置环境变量 LIVE_TRADING=1 才能启动实盘机器人。当前部署只读取行情与账户，不会向币安发送任何订单。

（実弾の発注安全ゲートが未開放：サービス起動時に環境変数 LIVE_TRADING=1 を設定しないと実弾ボットを起動できません。現在の配備は相場と口座を読み取るだけで、Binance に注文を一切送信しません。）

これは**意図的な安全ゲート**です。デフォルトでは Binance に対して完全に読み取り専用で、「实弹启动」（実弾で開始）を押しても実際には発注されません。実際に実弾で発注するには、**サービスを再起動**するときに次を付けてください：

```powershell
$env:LIVE_TRADING="1"; node server.js    # Windows PowerShell
LIVE_TRADING=1 node server.js            # macOS / Linux
```

起動ログが「实盘下单：已关闭（安全闸，只读）」から「**已开启**」（有効）に変わります。変わらなければ環境変数が反映されていません（cmd を使ってしまった、または変更後に再起動していない可能性が高いです）。

### Q23：実弾モードの口座ページでデータが読めないのはなぜですか？

プログラムはクラッシュせず、具体的な理由を返します：

| ページの表示 | 原因 | 対処 |
| --- | --- | --- |
| 尚未配置 API Key（API Key が未設定） | まだ追加していない | 「API Key」ページで追加する |
| 缺少 API Secret（API Secret が不足） | Key だけ入力した | Secret を追加する |
| 已保存但尚未验证通过（保存済みだが検証未通過） | 検証を押していない、または検証に失敗 | 検証を押して具体的なエラーを確認する |
| 无法连接币安：…（Binance に接続できない：…） | ネットワーク不通／遮断／プロキシが必要 | 下記の切り分けを参照 |

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://fapi.binance.com/fapi/v1/time  # 期望 200
curl -s https://api.ipify.org; echo                                            # 出口 IP
timedatectl status                                                            # 时间要准
```

送信元 IP は Key の IP ホワイトリストと一致している必要があり、一致しないと `-2015` が返ります。時刻がずれていると `-1021` が返ります。

### Q24：ボットが手動で建てたポジションを決済してしまうことはありますか？

**いいえ、ありません。** ここはプロジェクト全体で最も慎重に扱っている部分です。

Binance の両建てモードでは、同一銘柄のロングは**アカウント単位で集約**されるため、取引所側はどの注文を誰が建てたかを区別できません。そこでプログラムは `state_json` の中で「このボット自身のポジション台帳」を保持し、毎ラウンド取引所と突き合わせます：

- 取引所の数量が**台帳より多い** → 手動ポジションと判断し、「检测到 多/空 有 N 张非机器人仓位（手动仓），机器人不会动它」（ロング／ショートに N 枚のボット以外のポジション（手動ポジション）を検出しました。ボットはこれを操作しません）と 1 件記録し、その後は放置します。
- 取引所の数量が**台帳より少ない** → あなたが手動で一部決済したとみなし、台帳を同期的に縮小します。

決済も「自分の台帳にある数量」だけを `reduceOnly` 付きで行うため、越境することはありません。**唯一の例外**は、実弾ボットで「リセット」を押した場合です。台帳が空になった後、取引所上のポジションは持ち主のいない「手動ポジション」となり、以降ボットはこれを管理しません。

### Q25：利確／損切りはプログラムが見て決済するのですか、それとも取引所に注文を置くのですか？

プログラムは **5 秒**ごとに価格を確認し（この間隔は環境変数 `TICK_INTERVAL_MS` で変更できます）、価格に達したら自ら成行で決済します。実弾モードでは**同時に** `TAKE_PROFIT_MARKET` / `STOP_MARKET` の条件注文も同期して発注し（トリガー価格はマーク価格を使用）、60 秒ごとに突き合わせて古い注文を取り消し新しい注文を出します。両方を併用する意味は、**プログラムが落ちても、ネットが切れても、PC の電源が切れても、取引所側に保護注文が残る**ことです。条件注文はボット自身の数量だけを対象とし、手動ポジションには触れません。発注に失敗した場合はイベントとして記録され、黙って失敗することはありません。

### Q26：「両建てモード」は有効にする必要がありますか？サーバー再起動後もポジションは残りますか？

**有効にしてください。** プログラムは両建てで発注し、ロングには `LONG`、ショートには `SHORT` を付けます。Binance 先物の画面 → 右上の設定 →「持仓模式」（ポジションモード）→ 両建て（切り替える前にすべてのポジションを決済する必要があります）。

再起動後：**ボット**は自動復旧し、**ポジション**は取引所に残ったまま（再起動で決済されることはありません）、**台帳**はデータベースに保存されているのでそのまま使われ、自分で建てたポジションを手動ポジションと誤認することはありません。

## 六、エラーコード対照表

### Q27：Binance の `-1xxx` は結局どういう意味ですか？

| コード | 意味 | プログラムの処理 | あなたがやること |
| --- | --- | --- | --- |
| `-1021` | 时间戳超出允许范围（タイムスタンプが許容範囲外） | 自動で時刻を再校正し、1 回だけ再試行 | システム時刻を合わせる |
| `-1022` | 签名不对（署名が正しくない） | 再校正してから 1 回だけ再試行 | Secret を貼り直す |
| `-1111` | 数量小数位太多（数量の小数桁が多すぎる） | 精度を自動で下げて再送 | 通常は何もしなくてよい |
| `-4164` | 金额/精度不达标（金額／精度が基準を満たさない） | `-1111` と同じ | 初回金額を大きくする |
| `-1106` | 不该带 reduceOnly 却带了（reduceOnly を付けてはいけないのに付けた） | ポジションモードに応じて回避済み | Binance のポジションモードを確認する |
| `-2019` | 保证金不足（証拠金不足） | 翻訳せず、原文をそのまま表示 | レバレッジを下げる、ポジションを小さくする |
| `-2015` | Key 错/没权限/IP 不符（Key が誤り／権限なし／IP 不一致） | 「API Key 或 Secret 错误，或密钥没有合约账户读取权限」（API Key または Secret が誤っているか、キーに先物口座の読み取り権限がありません）と表示 | 権限と IP ホワイトリストを確認する |
| `-1003` | 请求太频繁被限频（リクエストが多すぎてレート制限） | エラーとして記録し、次ラウンドで再試行 | ボットの数を減らす、周期を長くする |
| `-1007` | 服务器超时，不知成交没（サーバータイムアウト、約定したか不明） | 注文 ID で照会し、二重発注しない | 通常は何もしなくてよい |
| `-4046` | 重复设置同一参数（同じパラメータを重複設定） | 成功とみなす（レバレッジは既に目標値） | 何もしなくてよい |
| `-2013` | 订单不存在（注文が存在しない） | 決済済みとみなし、台帳を同期 | 通常は何もしなくてよい |

### Q28：`-1021` / `-1022` のタイムスタンプと署名エラー

**原因**：Binance はすべてのリクエストにタイムスタンプを要求し、それが `recvWindow`（本プロジェクトでは 5000 ミリ秒）以内である必要があります。マシンの時刻が数秒ずれるだけでタイムアウトと判定されます。

**プログラム**：バックグラウンドで 60 秒ごとに Binance と時刻を合わせ、`-1021`/`-1022` に遭遇すると**強制的に再校正してから 1 回再試行**します。

**あなた**：ずっと出るならマシンの時刻が本当にずれています。Linux では `sudo timedatectl set-ntp true`、Windows では「設定 → 時刻と言語 → 今すぐ同期」を実行してください。時刻に問題がないのに `-1022` が出る場合は、ほぼ確実に **Secret の貼り間違い**です（余分な空白、文字の欠落）。

### Q29：`-1111` / `-4164` の精度エラー

**原因**：Binance は先物ごとに数量の最小小数桁を定めており、例えばステップが 0.01 のとき 0.019 を発注すると拒否されます。

**プログラム**：その先物の実際の `stepSize` に従って**段階的に精度を落として再送**します。通常は最初の再送で成功するため、普段このエラーは目にしません。

**あなた**：`-1111` が繰り返し出る場合は、精度ルールを取得できていない可能性が高いです（ネットワーク問題でフォールバック値を使用）。`data/rules-cache.json` を削除してサービスを再起動し、再取得させてください。`-4164` が繰り返し出る場合は精度ではなく、**その金額が本当に小さすぎる**ことがほとんどです。割当資金か初回比率を大きくしてください。

### Q30：`-1106` の reduceOnly 関連

**原因**：`reduceOnly` は「決済のみで新規建玉はしない」というフラグです。Binance では**両建てモードでこれを送ると即座に拒否**され、片方向（ワンウェイ）モードでのみ必要です。

**プログラム**：すでに区別しています。両建て（`positionSide` が `LONG`/`SHORT`）では**送らず**、片方向モードでのみ送ります。

**あなた**：それでも遭遇する場合は、Binance 側のポジションモードが「片方向モード」に切り替わっていないか確認し、両建てに戻してください。

### Q31：`-2019` 証拠金不足

**原因**：この 1 筆を建てるために使える証拠金が足りません。「足りない」は資金がないとは限らず、他のポジションに占有されているか、このボット自身が予算を使い切っている可能性もあります。

**プログラム**：このエラーは**専用の翻訳がなく**、Binance の英語原文がそのまま表示されます（「币安接口错误：Margin is insufficient.」＝Binance API エラー：証拠金が不足しています、のような形）。

**あなた**（順番に）：①「账户」（口座）ページの可用残高がこの証拠金に足りているか確認する。②「第一笔保证金占比」（初回証拠金の割合）を小さくするかレバレッジを下げる（**レバレッジが低いほど、同じ名目で占有する証拠金は増えます**）。③ 複数のボットを同時に動かして証拠金を使い切っていないか確認する。④ 実弾口座に既にある手動ポジションも証拠金を占有するため、プログラムの問題ではない可能性もあります。

## 七、セキュリティ

### Q32：API Key はどこに保存されますか？安全ですか？

ローカルの `data/app.db` に保存され、**平文ではありません**：

| 項目 | 方式 |
| --- | --- |
| 暗号化アルゴリズム | **AES-256-GCM**（完全性検証付き。改ざんは検出されます） |
| 鍵の取得元 | `data/master.key`（32 バイトの乱数、パーミッション `0600`） |
| 画面表示 | マスクされた Key のみ（先頭 4 文字 ＋ アスタリスク ＋ 末尾 4 文字） |
| ログインパスワード | `scrypt` ＋ ユーザーごとに独立した乱数ソルトのハッシュ ＋ 時間一定比較 |

**データベースファイルを入手しても `master.key` がなければ Key は復号できません。**

### Q33：`data/master.key` を失うとどうなりますか？

**すでに保存済みの API Key は永久に復号できません。** 症状としては、ボットは起動できるものの、Key の一覧を開くと復号失敗のエラーになります。

- **バックアップがある場合**：`master.key` と `app.db` を**セットで**復元してください（必ず 1 組で、どちらか一方を差し替えると一致しません）。
- **バックアップがない場合**：古い Key を削除して登録し直すしかありません。`master.key` は自動的に再生成されます。環境変数 `BT_MASTER_KEY`（64 桁の 16 進数）で鍵を固定することもできますが、環境変数はサーバー上の他のプロセスからも見えます。**唯一確実な方法は、バックアップ時に `data/` を丸ごとコピーしておくことです。**

### Q34：公網に置いてスマホからアクセスできますか？HTTPS は必須ですか？

**可能ですが、2 つのことを必ず行ってください**：① 前面に **HTTPS リバースプロキシ**（Nginx ＋ 証明書）を置き、Node は引き続き `127.0.0.1` だけで待ち受ける。② ファイアウォールは 22/80/443 のみ開放し、`8787` を絶対に公網へ直接露出させない。

**なぜ HTTPS が必須か**：ログインパスワードも API Key も HTTP リクエストボディで送られるため、HTTP では平文となり、同じ WiFi にいる人や経路上のノードから見えてしまいます。設定方法は [DEPLOY.ja.md](../../DEPLOY.ja.md) の第 5 節を参照してください。

### Q35：`data/` ディレクトリを git にコミットしてもいいですか？

**絶対にできません。** 中には `app.db`（暗号化された Key、パスワードハッシュを含む）と `master.key`（復号鍵）があり、両方が漏れると Key がそのまま使えてしまいます。

なお SQLite は WAL モードなので、`data/` 下には `app.db`、`app.db-wal`、`app.db-shm` が同時に存在します。**バックアップ／コピーの際はまとめてコピー**してください。`app.db` だけをコピーすると直近の書き込みが失われる可能性があります。

## 八、配備と運用

### Q36：サーバー上で動かし続けるにはどうしますか？

Linux では **systemd** で常駐させ、起動時の自動開始とクラッシュ時の自動再起動を設定します。完全な unit ファイルは [DEPLOY.ja.md](../../DEPLOY.ja.md) の第 4 節を参照してください。要点は、unit に環境変数（`HOST`/`PORT`/`LIVE_TRADING`）を正しく書き、`WorkingDirectory` をプロジェクトルートに向けることです。そうしないと `data/` が別の場所に作られます。

### Q37：リバースプロキシと HTTPS はどう設定しますか？

[DEPLOY.ja.md](../../DEPLOY.ja.md) の第 5 節を参照してください（Nginx の設定、certbot の証明書、サブパス配備では `BASE_PATH` の設定が必要）。最も踏みやすい落とし穴は、リバースプロキシが `Host` と `X-Forwarded-Proto` ヘッダーを必ず透過させることです。そうしないとバックエンドが HTTPS リクエストを HTTP とみなし、ログイン状態が原因不明に切れます。

### Q38：バックアップ、アップグレード、ロールバックはどうしますか？

**`data/` ディレクトリ全体をバックアップ**してください。特に `app.db`（アカウント／ボット／注文／履歴）と `master.key`（失うと Key がすべて無効）が重要です。毎日定時にパッケージ化して別の場所に保管し、アップグレード前には必ずバックアップしてください。バックアップファイル自体も機密データなので、公開のクラウドストレージや git リポジトリに置かないでください。アップグレード／ロールバックの手順は [DEPLOY.ja.md](../../DEPLOY.ja.md) の第 7 節を参照してください。

## 九、それでも解決しない場合

次の順番で確認してください：① **ボット詳細ページのイベントログ**——プログラムの各ステップの判断がここに書かれており、9 割の問題は原因がそのまま分かります。② **ターミナル／サービスログ**（`journalctl -u <サービス名> -n 100 --no-pager`）。③ [DEPLOY.ja.md](../../DEPLOY.ja.md) 第 8 節のトラブルシューティング。④ プロジェクトリポジトリで Issue を作成する。

> ⚠️ ログを貼る際は、API Key、Secret、サーバーの IP、アカウントのパスワードを**必ず削除**してください。
